# 站立识别（输入视频 → 输出渲染视频）

基于本目录下的 `yolo26s-pose.pt`（YOLO26s 姿态估计模型）实现的站立/非站立识别算法。
输入一段视频，输出**带骨架、人体框、姿态标签和实时统计的渲染视频**，并可导出逐帧判定
结果（CSV）与轨迹级汇总（JSON）。

默认**只标注站立的人**（其余人不画框不画骨架）。解码 / 推理 / 编码全部走 GPU
（NVDEC → CUDA → NVENC），4K 监控视频端到端 **10.5 → 33~50 FPS**。

```bash
python stand_detector.py --source input.mp4 --output output/result.mp4
```

## 2. 算法原理

### 2.1 整体流程

```
ffmpeg 管道(NVDEC 解码 + 缩放 720p) ──► 批量推理(batch=8, FP16)
        ──► 逐帧驱动 ByteTrack（稳定 ID，用于时序平滑）
        ──► 几何特征提取（6 项，可解释）
        ──► 加权打分 = 站立置信度 score ∈ [0,1] + 证据覆盖率 coverage
        ──► 规则判定：站立 / 坐蹲 / 躺卧 / 未知
        ──► 时序平滑（滑窗均值 + EMA + 滞回 + 连续帧确认）
        ──► 渲染（骨架、框、标签、置信度条、HUD）
        ──► ffmpeg 编码(NVENC + 复用原音轨) ──► 渲染视频
        ──► 导出：逐帧 CSV、轨迹级 JSON（含每人站立时间段）
```

### 2.2 六个几何特征（站立时应该是什么样）

| 特征 | 含义 | 站立 | 坐/蹲 | 权重 |
|---|---|---|---|---|
| `torso_verticality` | 躯干向量与竖直方向的夹角余弦 | ≈1.0 | 也常≈1.0 | 3.0 |
| `leg_drop_ratio` | 髋→踝垂直距离 / 躯干长 | ≈1.6 | ≈0.8 | 3.0 |
| `knee_angle` | 膝盖夹角 | ≈170° | ≈90° | 2.0 |
| `body_extension` | 头→踝垂直距离 / 躯干长 | ≈3.0 | ≈2.0 | 2.0 |
| `bbox_aspect` | 人体框 高/宽 | ≈2.5~3.5 | ≈1.3~1.8 | 1.5 |
| `hip_height_ratio` | 髋→踝垂直距离 / 框高 | ≈0.5 | ≈0.35 | 1.0 |

每项特征按经验区间线性归一化到 `[0,1]`（例如 `leg_drop_ratio`：≤0.95 记 0 分，≥1.35 记 1 分），
再加权平均得到 **站立置信度 score**。权重与区间集中在 `stand_detector.py` 顶部的
`FEATURE_WEIGHTS` / `FEATURE_RANGE`，便于按场景调整。

**缺失特征不参与投票**：腿部被课桌挡住时无法计算 `leg_drop_ratio`，算法不会瞎猜，而是降低
`coverage`（证据覆盖率）。`coverage = 可用特征权重 / 总权重`。

### 2.3 判定规则（含"证据充分性"策略）

```
coverage < 0.30                       → 未知      （几乎无有效关键点）
看不到腿（无腿部证据，默认策略）        → 未知      （关键：避免把"坐在桌后只露上半身"判成站立）
躯干近水平 且 人体框偏宽               → 躺卧
score ≥ 站立阈值                      → 站立
否则                                  → 坐/蹲
```

> **为什么"看不到腿"要判未知？** 坐姿的人躯干同样竖直，仅凭上半身无法区分"站着"和"坐在桌后"。
> 实测：早期版本把教室里坐在课桌后的学生大面积误判为站立（假阳性），加入该策略后误判消失。
> 若你的场景里站立者经常只露上半身，可用 `--torso-only judge` 恢复宽松模式（结果带 `?` 低置信标记）。

### 2.4 时序决策：帧级补框 + 轨迹级三状态 Viterbi（防"突然断开"）

> 本工具所有**算法窗口一律以帧为单位**（`--bridge-frames`、`--viterbi-window`、`--draw-grace`、
> `--recheck-every`、`--relink-frames`、`--evidence-grace`），与视频帧率无关；
> 只有 `--start-time/--end-time` 用秒，因为它们用于在长视频里定位片段。

实测（3 机位 × 90s 4K 片段）：**70~83% 的站立时间段内部有"跟踪缺帧空洞"**，单次漏检
p50=1~2 帧、p90=10~12 帧、最长 31 帧，这才是画面上"绿框突然消失"的主因（降低检测阈值无效）。
因此时序层做两件事：

**① 帧级补框（TrackBridge）**

* 每个轨迹缓存末次实测的框/关键点/判定结果；漏检时从跟踪器 `lost_stracks` 取回该 ID 的
  **卡尔曼预测框**（会按运动方向继续外推），取不到则用末次框。
* 补框帧的观测值给**中立值 0.5**，并在 CSV 标记 `held=1`，完全交给时域逻辑推断。
* 超过 `--bridge-frames`（默认 **38 帧**）仍未检测到 → 注销该轨迹的解码器，站立时间段
  **收尾到末次真实观测时刻**。
* ID 重连：新 ID 在 `--relink-frames`（默认 10 帧）内出现且与刚消失轨迹的末次框 IoU ≥ 0.5
  时，继承其解码器状态。
* **冷启动防护**：实测证据不足 2 帧时不允许进入 S2（轨迹第一帧即使高分也不判站立），
  避免单帧误检被放大。

**①′ 定向补检（`--recheck`，默认开启）** —— 取代"画外推幽灵框"

* 站立轨迹漏检时，在末次框外扩 25% 裁剪并用姿态模型重新检测（`--recheck-imgsz`，默认 480）。
* 命中（实测 40~78%）→ 视为**真实观测**：拿到真实框与关键点，照常分类、更新状态与绘制。
* 未命中 → 保留状态但**不画幽灵框**；仅当最近一次确认 ≤ `--draw-grace`（默认 4 帧）时
  沿用该框，肉眼不可辨。
* 开销控制：只补站立轨迹、每帧最多 `--recheck-per-frame`（默认 2）条、失败后退避
  `--recheck-every` 帧；轨迹需累计 `--recheck-min-det`（默认 2）次真实检测才允许补检。
* 实测代价：4K→720p 由 83 FPS 降到 41~48 FPS（在批量异步流水里插入同步检测的开销）。
  需要速度时改 `--no-recheck --bridge-frames 10`（≈90 FPS，幽灵框最多 10 帧）。

**①″ 精度门槛（`--standing-min-score`，默认 0.80）**

* **平滑置信度 < 0.80 的站立估计不标注、不计数**（HUD、CSV `is_standing`、JSON
  `standing_person_frames` / `standing_intervals` 一致口径）。
* 时序状态机本身不受影响：CSV 新增 `s2_state`（原始 S2 状态）与 `smooth_score`（用于门槛
  与显示的平滑置信度），JSON 新增 `totals.s2_person_frames` 与 `algorithm.standing_min_score`，
  便于区分"状态判为站立"与"按精度输出"。
* 实测（stand_v 三机位 90s 片段）：门槛滤掉 11%~18% 的 S2 帧，被滤帧的平滑置信度
  中位 0.74、上限 0.800；所有标注帧的平滑置信度 ≥0.80。

**①‴ 绘制与检测解耦（重要修复）**

* 标注一律画在帧副本上（`canvas = frame.copy()`），原始帧保持干净供**定向补检**裁剪使用。
* 修复前补检是在"已经画好骨架/框"的帧上裁剪，导致**绘制模式会反过来影响判定结果**
  （同片段 `--no-skeleton` 与默认模式的 S2 帧数相差 7%~30%）；修复后三种绘制模式结果
  完全一致（实测 S2 帧数、补检命中数逐帧相同），且补检命中数提升（干净帧更易检出）。

**①⁗ 标注层去重（`--dedup-iou`，默认 0.60）+ 僵尸轨迹阻断**

* 实测诊断：重复框**不是**检测层/跟踪层 NMS 的问题（检测层 1400 帧仅 39 对重叠、跟踪输出仅
  18 帧各 1 对），而是"补框 + 补检"把失效轨迹反复复活——曾经同一人被 9 个 ID 标注、框几乎重合。
* 处理：每帧把"真实检测 / 补检命中 / 沿用帧"收进候选列表，按优先级（真实检测与补检命中 >
  沿用）贪心抑制：IoU 超阈值的框**不绘制、不计数**，但仍在 CSV 保留并标 `dup=1`。
  每帧站立人数、CSV `is_standing`、JSON 时间段全部基于去重后的结果（画面 = 计数 = 数据）。
* 僵尸阻断（`--zombie-iou`，默认 **0.15**）：补检命中框若与本帧已确认的其它轨迹重合，**不算作
  确认**（不刷新确认时间），该轨迹会在 `--bridge-frames` 后正常注销。这个阈值可以比显示去重更严，
  因为它只作用于"本帧没检测到"的轨迹——相邻两人每帧都有真实检测，不会因此被误合并。
* 实测效果（stand_v 三段）：IoU>0.6 的重复框 **1799/1799/878 帧中仅 1/0/0 帧**（改造前
  IoU>0.5 的帧占比 70.7%/72.2%/41.5% → 现 2.5%/0.6%/0.9%）；**长期重叠轨迹对 12 → 4/2/1 对**，
  且剩余各对（平均 IoU 0.25~0.40）经 4K 原帧裁剪复核为**相邻两人**（如 id33-43），非重复。
* 已知边界（实测四种判据都不足以区分）：**重复对 vs 相邻两人**在框几何上高度重叠——
  IoU（重复 0.60/0.31~0.49，相邻 0.47/0.40）、框中心相对距离（重复 0.71~0.76，相邻 0.42）、
  包含度（重复 —、相邻 0.59）、**颜色直方图相关性（重复 0.71~0.76，相邻 0.77~0.92）**，
  区间全部交叠，没有可用阈值。因此**残余的偶发双框无法靠几何/廉价外观判据可靠去除**；
  彻底解决需要身份特征（ReID 嵌入）逐对判定，本机 ONNX GPU 因缺 cuDNN 9/CUDA 13 无法启用
  （见 2.5 的实测），若走 torch 侧的特征提取需另接模型。
* 残余规模（最终交付）：IoU>0.6 的重复框 **1/0/0 帧**；IoU 在 0.5~0.6 的帧 45/11/8 帧
  （占标注帧 2.5%/0.6%/0.9%），其中部分经复核确为相邻两人（如 id33-43）。
* 站立段结构不受去重影响：同一片段在僵尸阈值 0.60/0.30/0.15 下均为 **50 个站立段**，
  减少的只是重复帧（5446 → 5008 → 4663 帧）。

**①⁵ 近距/被画面切断目标：裁剪放大重检**

* 触发：框高 ≥ `--near-ratio`（默认 0.50）画面高，或可见关键点越界比例 ≥ `--near-kpt-out`
  （默认 0.30）。裁剪框外扩 15%（裁到画面内）后按 `--near-imgsz`（默认 640）重检——裁剪区小于
  整帧，目标在模型输入中的像素尺寸显著变大（整帧 0.5 倍 → 裁剪约 1.3 倍）。
* 重检命中同一人（IoU ≥0.30）且**覆盖度更高**时替换该帧判定；每帧最多 `--near-per-frame`
  （默认 2）次。实测触发极少（53/156/0 次），对速度无影响。

**①⁶ 摄像头正下方的透视压缩补偿（`--persp-calib` / `--no-persp`）**

* **问题定位（stand_v 实测）**：正下方的人**不是检测不到**——197 行贴底边记录里标签为
  STANDING、关键点覆盖度 1.0、膝角中位 170.6°、躯干倾角 9.9°（与其它位置 174.3°/10.5° 一致），
  但**俯视透视把纵向几何压扁**：髋-踝跨度/躯干长 1.03 vs 1.42、框高/宽 2.12 vs 2.74，
  分数掉到 0.66~0.74，被 0.80 精度门槛滤掉（另有 112 行未进 S2）。
* **做法**：按"框底 y"自动标定压缩曲线 —— 预扫采样（短片逐帧抽样、长片只解关键帧，
  跨整段覆盖）→ 只用与俯角无关的"明确站立"样本（覆盖度 1.0、膝角≥160°、躯干≤30°）
  → 滑动窗口中位数求各 y 处的压缩比 → `k(y)=clamp(ref/median, 1, --persp-max-k)`、
  单调化后存为分段线性曲线；打分时把 `leg_drop_ratio`、`body_extension`、`bbox_aspect`
  乘上对应 k（`torso_verticality`、`knee_angle`、`hip_height_ratio` 视角不变，不动）。
* **两条结构性保证**：① 补偿只做乘法且 `k ≥ 1`，而打分是单调不减的加权平均 →
  **分数只会升高**，现有能过门槛的目标不可能被取消；② 只对 `y ≥ --persp-y0`（默认 450px）
  生效，上半画面逐位一致。
* **自动标定失败会安全回退**：样本 <200 时状态标 `insufficient_data`、k=1（等同关闭）。
  同一机位可用 `--persp-calib <file>` 复用曲线（第二次运行 0 成本，实测 15.2s → 0.0s）。
* **实测效果（stand_v）**：贴底边 STANDING 行标注率 **0/111 → 128/132（97%）**、
  2/19 → 21/21（100%）；**旧标注丢失 0 个、非近区丢失 0 个**（人员级 IoU≥0.5 匹配）；
  无近区样本的机位自动回退、输出逐帧不变。

**② 轨迹级三状态 Viterbi（temporal.py）**

* 隐状态：`S0` 非站立 / `S1` 起立·坐下过渡 / `S2` 稳定站立；**只有 S2 会被标注与计数**。
* 转移只允许 `S0↔S1`、`S1↔S2`，**`S0↔S2` 概率为 0**：单帧从"非站立"跳到"站立"在数学上
  不可能，必须经过过渡态 → 单帧误判造成的频闪被结构性消除（实测：单帧/两帧高分尖峰 0 误报）。
* 发射模型由既有阈值推导（μ1=(0.45+0.60)/2、μ2=2×0.60-μ1、μ0=2×0.45-μ1，σ 由
  `--viterbi-sigma` 控制），因此"0.60 进站立 / 0.45 退出"仍是状态翻转的临界点。
* **中立观测**（补框帧、无腿部证据帧）不参与发射，状态由转移矩阵决定；因此短遮挡不会掉出站立。
* 每个轨迹维护 `--viterbi-window`（默认=补框窗口）帧 FIFO，每帧在窗口内求全局最优路径，
  只提交最新帧状态（因果滑窗，实时/离线一致）。防抖强度由 `--viterbi-stay`（默认 0.92）控制。
* **无证据预算**：检测到人但连续看不到腿超过 `--evidence-grace`（12 帧 ≈0.6s）后，改为施加
  持续向下的证据，避免"坐着但腿被桌子挡住"的人被无限期判为站立。

输出每人的**站立时间段**（S2 连续区间），并支持跳帧、遮挡、短暂丢失与 ID 切换。

### 2.5 I/O 层（本机实测的加速点）

> **关于 ReID**：曾按"用外观特征维持身份连续"的思路实测过 BoT-SORT + ReID
> （`yolo26n-reid.onnx`）。结论是**对本场景无收益**：三种跟踪器在 90s 片段上的缺帧段完全
> 相同（ByteTrack 74 段 / BoT-SORT 74 段 / BoT-SORT+ReID 75 段，总缺帧 282/281/282），
> 换 ID 次数本来就≈0，而 ReID 单帧多花 22.6 ms（且本机 onnxruntime-gpu 因缺 cuDNN 9
> 无法启用 CUDA EP，实际跑在 CPU 上）。漏检是"人在整帧尺度下太小"造成的，属于检测问题，
> 因此改用**定向补检**（见 ①′），而不是 ReID。

> **stand_v 三视频实测（0.80 门槛，各取 90s 片段）**：教室前端_左(12:24 场次) 39.2 FPS、
> S2 10705 → 输出 9538 帧、最大同时 13；教室前端_左(12:41 场次) 38.0 FPS、9762 → 8018、
> 最大同时 8；教室尾端_右 40.4 FPS、2341 → 1781、最大同时 4。骨架版与无骨架版的分析结果
> 逐帧一致（绘制不参与判定）。

| 环节 | 旧实现 | 现实现 | 实测 |
|---|---|---|---|
| 解码 4K HEVC | cv2 在 Python 里搬 24 MB/帧 | ffmpeg 管道内 NVDEC 解码并缩放到目标分辨率 | 50 ms → 6.5 ms/帧 |
| 推理 | `model.track` 逐帧 | batch=8 批量 `predict` + 手工驱动 ByteTrack | 28.5 ms → 5.7 ms/帧 |
| 编码 | libx264 medium（720p 上限 28.7 FPS） | h264_nvenc（281 FPS），独立线程 + 有界队列 | 不再阻塞主循环 |
| 跳转 | cv2 `POS_MSEC`（开 GOP 素材会解出错帧） | 混合跳转：先快跳到目标点前 10s，再精确裁剪 | 86.8s → 1.9s，且逐像素一致 |

跳转方式（`--seek`）：`hybrid`（默认，推荐）/ `accurate`（顺序解码到目标点，最慢但绝对可靠）/
`fast`（仅关键帧对齐，**监控 HEVC 会解出坏帧，不建议**）。

## 3. 输出说明

### 3.1 渲染视频

**默认 `--annotate standing`：只标注站立的人**，画面里其余人（坐着/未知）完全不画，
便于一眼看出谁站起来了。HUD 仍统计全部人数。需要旧的全标注效果时加 `--annotate all`。

* **骨架**：躯干/腿部加粗，其余为亮度 85%；每人独立配色。
* **人体框 + 标签**：颜色对应状态（绿=站立、橙=坐/蹲、红=躺卧、灰=未知）；
  **标签不含编号**、站立写英文首字母大写（如 `Standing 0.95`）并使用平滑后的置信度；
  `?` 表示低置信（证据不足的推定），`~` 表示单帧结果与稳定状态不一致；
  **虚线框**=该帧证据不足（覆盖率 <0.50，通常是腿部被遮挡的推定）。
* **补框帧**：漏检期间用卡尔曼预测框继续标注，外观与实时检测**完全一致**（数据里用 `held=1` 区分）。
* **去重**：同帧内重叠的重复轨迹只保留一个框（其余在 CSV 标 `dup=1`），见 ①⁗。
* **HUD 面板**：帧号/FPS/时间、`Standing N`（**不显示总人数、不显示模型名**）、阈值参数；
  标签下方**不再绘制置信度进度条**。
* **图例**：左下角四色图例。

### 3.2 CSV（逐帧逐人）

`frame, time_s, track_id, label, is_standing, score, coverage, torso_angle_deg,
leg_drop_ratio, knee_angle, bbox_aspect, x1, y1, x2, y2, held, smooth_score, s2_state, dup`

其中 `is_standing` 为时序状态 S2 的判定结果，`held=1` 表示该帧由补框（卡尔曼预测）产生，
`score=0.5` 为中立占位值、特征列留空。
`is_standing` 已包含 **0.75 精度门槛**（平滑置信度 ≥0.75 才为 1）；`s2_state` 是未经门槛的
原始时序状态，`smooth_score` 是门槛与标签显示使用的平滑置信度。
`is_standing` 已包含 **0.80 精度门槛**；`dup=1` 表示该行因去重（或超出沿用窗口）**未被绘制、
未被计数**，数据仍保留便于追溯。

### 3.3 JSON（汇总）

关键字段：`video`（分辨率/fps/帧数/跳转方式）、`io`（读帧方式/hwaccel/编码器/批量/解码错误数）、
`performance`（稳态 FPS、预热耗时、`stages_ms{read,infer,track,draw,encode}`）、
`algorithm`（`temporal_model=viterbi3`、`bridge_frames`、`viterbi_window/stay/sigma`、
`recheck{enabled,imgsz,pad,per_frame,every,min_det,draw_grace,relink_frames,hits,tries}`）、
`totals`（`state_histogram{S0,S1,S2}`、站立帧占比、`held_person_frames`、最大同时站立）、
`tracks[]`（每人 `standing_intervals`、`held_frames`、`state_seconds`）。

## 8. 已知限制

* **补检代价**：默认（补检开）4K→720p 为 41~48 FPS；关闭补检可到 ~83 FPS，但漏检期间会保留
  最多 `--bridge-frames` 帧的旧框（滞留感即来自这里）。
* **未确认帧**：补检没命中的帧沿用最近确认框，最多 `--draw-grace`（默认 4 帧），数据里用 `held=1` 标记。
* **补框上限**：漏检超过 `--bridge-frames`（默认 38 帧）时注销轨迹；人真正离开后最多多显示
  `--draw-grace` 帧（补检模式）。
* **透视补偿的适用边界**：曲线以"框底 y"为自变量，仅对**固定机位**成立；换机位/分辨率需重新
  标定（`--persp-calib` 会校验分辨率并告警）。若某机位在前若干采样里没有"明确站立"样本，
  标定会回退为不补偿（状态写入 JSON），此时可指定由同时段/同机位其它视频算出的曲线。
* **无证据预算**：检测到但连续看不到腿超过 `--evidence-grace`（≈0.6s）后，状态会向下衰减，
  因此"坐在桌后且腿部长期不可见"的人不会一直被标为站立。
* **遮挡**：腿部完全被遮挡且无历史站立证据时给出"未知"（可用 `--torso-only judge` 切换为推定模式）。
* **绘制成本**：默认只画站立者，720p 下约 2.6~5.5 ms/帧。
* **监控素材质量**：t_v 的 4K HEVC 文件为开 GOP 且有偶发坏帧，**不要用 `--seek fast`**；
  提取片段时用 `-fps_mode cfr` 补帧可保证时长与帧数一致。
* **2D 歧义**：蹲姿与坐姿在图像上接近，统一归为"坐/蹲"；躺卧仅在躯干近水平时触发。
* **多人重叠**：跟踪 ID 可能切换，可用 `--track-ttl` 与 `--tracker` 配置调整。
* 模型只输出人体姿态，不区分身份；如需人脸/工牌识别需另接模型。
